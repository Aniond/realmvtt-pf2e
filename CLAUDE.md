## Overview

This is a Pathfinder 2nd Edition ruleset implementation for Realm VTT. The codebase consists of HTML files with embedded JavaScript that interact with the Realm VTT API.

**Important**: This ruleset uses the Realm VTT API (https://www.realmvtt.com/wiki/ruleset-editor-and-api). HTML and JavaScript must be written to conform to this API. Field values cannot be directly embedded into HTML - all data access must go through the API.

## Architecture

### Data Path System

- `dataPath` - Current field's data path context
- `getNearestParentDataPath(dataPath)` - Navigate to parent object in data hierarchy
- `record` - The current record being edited
- Field paths use dot notation: `data.ancestries`, `fields.levelLabel.hidden`

### Modifier System - Critical for All Rolls

**Always check for relevant modifiers before making any roll** using `getEffectsAndModifiersForToken`:

```javascript
getEffectsAndModifiersForToken(record, modifierTypes, field, itemId, appliedById)
```

**Parameters**:
- `record` - The character/token record
- `modifierTypes` - Array of modifier types (e.g., `['saveBonus', 'savePenalty']`)
- `field` - **Third parameter (often required)** - The relevant field/context (e.g., 'fortitude', 'dex', 'perception')
- `itemId` - Fourth parameter - Only for attack rolls with specific items
- `appliedById` - Fifth parameter - Only when checking for effects from specific tokens

**Implementation Pattern**:
1. Always make TWO modifier checks:
   - Specific modifiers for the roll type
   - General modifiers using `['allBonus', 'allPenalty']` with the relevant attribute

2. Example for saving throws:
```javascript
// Get save-specific modifiers (e.g., fortitude bonus)
const saveMods = getEffectsAndModifiersForToken(
  record,
  ['saveBonus', 'savePenalty'],
  saveType // 'fortitude', 'reflex', or 'will'
);

// Get attribute-based all modifiers
const allMods = getEffectsAndModifiersForToken(
  record,
  ['allBonus', 'allPenalty'],
  attribute // 'con' for fort, 'dex' for reflex, 'wis' for will
);
```

**Note**: The field parameter may not be relevant for all modifier types, but include it when there's a relevant context.

### UI Conventions

- Lists use `_id` field with `generateUuid()` for unique identifiers
- Trait objects structure: `{ _id, name, identified, data }`
- Hidden field control via `fields.[fieldname].hidden` properties
- Conditional visibility based on data values

## Development Guidelines

### Working with HTML Files

1. All JavaScript must be within `<script>` tags in the HTML files
2. Functions can reference the global `record`, `dataPath`, and `api` objects
3. Use `api.setValues()` for all data modifications - never modify data directly
4. Always provide callbacks when chaining operations that depend on data updates

Fields such as `onload` and `onchange` only work on Realm VTT field HTML, not on plain elements like `div` or `span`.

### Adding New Features

1. Check existing patterns in similar files (e.g., other `-main.html` or `-list.html` files)
2. Use `generateUuid()` when adding items to lists
3. Implement `showHideFields()` for dynamic UI elements
4. Handle drag-and-drop via `onDrop()` functions

### Modifying Game Mechanics

1. Core mechanics are in `rollhandlers/common.js`
2. Proficiency calculations, ability scores, and modifiers are centralized
3. Use `onAddEditFeature()` to trigger recalculations after data changes

### Attack Log (multiple attack penalty, momentum traits)

`rollhandlers/attack-log.js` counts the attacks a creature makes on its own turn. It suggests and never enforces, since players make mistakes:

- Strikes keep their 1st/2nd/3rd buttons, which always set the penalty. The card doesn't compare the button with the count: a player can roll again before the last roll's result is logged, so the count can lag behind.
- Spell attacks and attack-trait skill actions (Grapple, Trip...) get the penalty from the count as a ticked modifier that can be unticked in the roll prompt.
- Forceful, twin, sweep and backswing apply from the earlier attacks, also as ticked modifiers.

Storage:

- `onTurnStart` sets the campaign variable `pf2eTurn` to `{ key, round, tokenId, recordId }`. The same token's turn starting again in the same round (Next after Previous) keeps the key and so the turn's log; any other turn start gets a new key. `onEncounterEnd` clears it, so a new encounter always starts a new log.
- The log is on the attacker's token at `data.turnAttacks` (`{ turnKey, attacks }`). It is written only by the result handlers (`attack.js`, `skill.js`) from `metadata.turnAttack`, which carries the log as it was at roll time. A log whose `turnKey` isn't the current turn's is ignored.

When adding a new kind of attack roll, pass `turnAttack` (from `getTurnAttackMetadata`) in the roll metadata and call `logTurnAttack` in its result handler. Attacks on another creature's turn (reactions) are not logged and take no penalty from the log.

### Stances and the action economy

`rollhandlers/action-limits.js` only swaps stances: applying a `Stance: ...` effect (`applyEffectButton`) first removes the creature's other `Stance: ...` effects. The ruleset doesn't police the action economy (flourish, press, finisher, hex, composition, spellshape): no warnings and no per-turn action log. The GM runs those at the table.

### Basic Saves (applied per target)

`rollhandlers/basic-saves.js` lets one damage roll be applied to many creatures by each one's own basic save.

- `rollSave` puts the saver's token in the roll metadata (`saverTokenId`, from `getSaverTokenRef`), and `basicSave: true` when the save button passed `{ basic: true }` (`getSaveMacro`'s `basic` argument; spells with the Basic box).
- `save.js` keeps the result on that token at `data.lastSave` (`{ degree, saveType, dc }`), and a basic save's card says what damage it takes.
- A damage card with `metadata.basicSave` (`{ saveType }`) has an Apply by Saves button. A spell's damage button sets it from the Basic box. An ability's damage buttons (`executeDamageMacro`) get it from `updateDamageMacros` when the description's save button is basic: the module converter writes `rollSavingThrow('reflex', 28, { basic: true })` for Foundry's `@Check[reflex|dc:28|basic]`, with `undefined` for the DC of one without a DC. Older imports without the flag get no button. `applyDamageBySaves` applies it to each selected creature by its most recent save (no time limit and no save-type check; the card names the save it used): none, half, full or double. Each damaged creature's damage card is headed by one bold line ("Fireball: applied by Reflex failure, full damage"); the rest share one card. A save is never marked used, so it can be applied again (another damage part, or redoing it).

### Animal companions (characters)

Animal companions are characters, as Foundry's PF2e Companion Compendia builds them. Their ancestry is the companion type, their class is "Animal Companion", and their stages (Mature, Nimble, Savage, Specialized) are feats, all in a data module. `rollhandlers/animal-companions.js` holds the ruleset's part; common.js calls it:

- `isAnimalCompanionCharacter`: the class is named Animal Companion, or has `data.animalCompanion: true`. Such a character:
  - has no Automatic Bonus Progression (`isAbpCharacter`) and gains no attribute boosts at Level Up (`getLevelUpGains`)
  - benefits only from item bonuses to AC and Speed (`withoutAnimalCompanionItemBonuses`, in `getEffectsAndModifiersForToken`; an effect rule's `-item` suffix is stripped first)
  - gets at most +3 to AC from item bonuses all told: its armor's (barding's, potency included, `getACForArmor`), and the rest of the +3 for any other
  - shows no free boost fields when its level is typed in by hand (`getFreeBoostFieldsForLevel`)
- Its attributes are `attributeBonus` modifiers on the ancestry's feature. Its ancestry has no boosts or flaws. `attributeBonus` values are added as numbers, and inactive ones are skipped.
- Modifiers the module's feats use:
  - `weaponDiceCount`: the number of base damage dice for matching weapons (`getAlteredWeapon`), the highest wins. Striking runes still add to it. Mature uses 2 and Specialized 3, with predicate `["item:category:unarmed"]`.
  - `creatureSize` value `"+1"`: one size larger, up to Large, adding up and counting from the ancestry's size (`getFeatureCreatureSize`). The rules say "grows by one size if it's Medium or smaller".
- The Notes tab shows an Animal Companion box only for a companion (`fields.companionProperties`, set in `onAddEditFeature`). It has the master (`data.companionMaster`) and a Match Master's Level button. Choosing the master, or the button, sets the companion's level to the master's (`syncCompanionLevel`) and works the sheet out again. There's no level-up hook, so a master's Level Up doesn't reach it on its own.
- Pictures:
  - Dropping a companion ancestry gives the character the ancestry's portrait, and its `data.tokenImage` (or portrait) as the token image. This only fills a picture that's still empty or a placeholder (`getCompanionImageValues`).
  - The Notes tab's **Use art from creature** picker copies any NPC's portrait and token (`onCompanionArtChange`), so a table's own licensed creature art can be used; the module ships none.
- Rules choices:
  - The module's README lists them under "Rules notes".
  - A specialization's "master if it was already expert from its type" is read literally: a savage Bully's Athletics stays expert, where Foundry raises it to master.
  - Barding is modeled as light and heavy armor proficiency.
  - No ABP is Foundry's convention, not a printed rule.
- Companions skip the creation wizard, which requires a key attribute and boosts. You make one by dropping the ancestry and the class on a new character.

### Concealment and detection

`rollhandlers/concealment.js` (Player Core pg. 442-447): a Strike or spell attack against a concealed target (DC 5), or a hidden, invisible or undetected one (DC 11), or from a dazzled (DC 5) or blinded (DC 11) attacker, carries the worst flat check as `metadata.concealment`. `attack.js` shows it as a line and a Flat Check button; nothing is rolled or refused automatically. A hidden, invisible or undetected attacker makes its target off-guard, applied to the AC as flanking is. Effects aren't per observer, so a condition on a token counts against everyone; the GM removes it when it no longer applies.

### Cover

`rollhandlers/cover.js` (Player Core pg. 424): Strike and spell attack prompts get `getCoverModifiers`, an unticked modifier ("Target AC +2 (Standard Cover)", "Target AC +1 (Lesser Cover: Goblin in the way)"), offered as a reminder like Blessed Swiftness. Cover is the GM's call (Sean, 2026-11-05: "be light on automation around cover"), so it only counts when someone ticks it. `getDetectedCover` asks the platform's `api.getCover(attacker, target, { method: "center" })`: its `degree` (walls, closed doors and windows, terrain, 3D props) is standard, greater or total cover, and a creature in its `creatures` with `centerLine` gives lesser cover, or standard when it's two or more sizes larger than both. Only the best applies. Dead creatures, hazards, vehicles and tokens hidden from the players (`visible: false`) don't count. Total cover gives no modifier. It adds only what it beats of the target's best circumstance bonus to AC (`getBestCircumstanceAcBonus`: modifiers, effects, and `getRaisedShieldAcBonus`). A target with an effect whose name starts with "Cover" is skipped: the GM placed it by hand. The `coverNotice` campaign setting (default Yes) floats the detected cover over the target, as Sean's 5e and Level Up rulesets do.

### Immunities, weaknesses and resistances

`applyDamage` reads them from `getIWR` and matches each damage type, then the roll's `metadata.damageCategories`. The categories follow Foundry's IWR types (`actor/data/iwr.ts`):

- "physical" means bludgeoning, piercing and slashing. "energy" means acid, cold, electricity, fire, sonic, force, vitality and void. Both are expanded into those types (`IWR_DAMAGE_GROUPS`) in the IWR lists, in "ignore ... resistance" modifiers and in suppressIWR.
- `withDamageCategories` adds the categories a roll's types don't carry:
  - "spells" for damage from a spell
  - "holy" or "unholy" when the attack or spell has that trait
  - "area-damage" when its source has an area: `getDamageSource` sets `damageSource.area` from `data.area`, and `updateDamageMacros` also from the ability's text ("in a 30 ft. Cone", `hasAreaText`), since the converted NPC data keeps the area only there. A bare NPC `executeDamageMacro('formula', 'category', 'name')` gets a context (`damageSource`, plus `basicSave` when there is one) when it has a basic save or an area.
  - "splash-damage" on a hit whose damage includes splash (`metadata.splashDamage`) and when splash damage is applied on its own
- Effect rules carry Foundry's exceptions, definition and doubleVs in the rule's `data`, as a feature modifier does in its own `data` (`getIWRModifierDetails`): `{ type: "resistance", value: "all-damage 5", data: { exceptions: ["force"] } }` (Ghostly Shift). `exceptions` is a list or comma text of words (a damage type, trait or material), or `[{ "definition": [...] }]` entries; `doubleVs` is a list or comma text of words.
- Weaknesses are checked for each damage type in the hit. Of those that apply to a type (its own, all damage, then each category), only the highest is added, with exceptions and doubleVs counted first: a demon weak to cold iron 5 and holy 5 takes +5 from a holy cold-iron weapon. A precision weakness is part of that choice for the type the precision damage rides on.
- Legacy data reads as remaster:
  - Damage types: positive becomes vitality and negative becomes void. Good and evil damage becomes spirit damage with the holy or unholy category.
  - Weaknesses, resistances and immunities: positive and negative become vitality and void, and good and evil become holy and unholy, keeping the stronger of a legacy entry and a remaster one.
  - Lawful and chaotic stay as they are.
- A token immune to a condition is asked about it (`getConditionImmunity` in `addConditionGain`, which every Apply button and maneuver goes through): its immunities list names the condition, or object immunities cover it. Vehicles and hazards have object immunities whether or not their data lists them (Foundry adds them to every hazard), nonlethal attacks among them. The GM can apply it anyway; nothing is refused.

### Scrolls and Wands (casting from items)

`rollhandlers/item-spells.js` lets Use on a scroll or wand cast its spell with the character's own spellcasting.

- A scroll or wand is found by its `scroll`/`wand` trait or item category (`getItemSpellKind`), never by its uses. Its spell is the Spell field or the first spell its description links (looked up by id, then by name); its rank is the Level field, "(3rd-Rank Spell)" in its name, or "at 3rd-rank" in its text.
- An automatic "Scrolls and Wands" entry (type `item`, `data.itemSpells: true`) follows the inventory: one row per scroll and wand at the item's rank, whose uses show the wand's use for the day or the scroll's count, and whose `data.itemSpell` (`{ itemId, itemIndex, itemName, kind, spellId }`) names its item. `syncItemSpells` brings it up to date when a scroll or wand is added (dropped on the sheet), equipped, counted, deleted or used; it reads the record again first, writes only the entry (`data.spells.<index>`; `api.addValue` when new, `api.removeValue` when none are left) and only when it changed. It never runs on sheet open. Realm runs every click as a script of its own (a fresh sandbox; top-level variables don't carry over), so two syncs can overlap and can't wait for each other. Each writes against a record it has just read (again after any spell look-up), only when something changed, and removes by id with `api.removeValueFromRecord` on that read (Realm pulls by `_id`, so two removing at once remove once; plain `api.removeValue` maps the index on the record bound when the script started, which can be stale). Two adding at once can leave a second entry; each sync reads again after writing and removes any but the first. A used-up scroll is found again by its id before it's removed, and stays if it's gone or restocked.
- Casting from a row (from the entry, or Use on the item, which syncs and casts the row) goes through `castSpell`: `getItemSpellCast` works out the caster's numbers for that spell (their best prepared or spontaneous entry of its tradition, or one that already lists it, Foundry's `canCast`) and spends the row's item, all in castSpell's one write, and the card says which item and with what. It never refuses: a spent wand still casts, with an overcharge line. An overlay spends nothing. A row from before rows named their item finds it by the spell's name.
- Anything that walks `data.spells` must leave that entry out of slots, uses and refills (`isItemSpellsEntry`); `rest` skips it, and the class sync and recalculation already leave unmanaged `item` entries alone.
- Without the tradition, it casts with Trick Magic Item's DC and attack (Player Core pg. 264: level as proficiency, the highest of Int, Wis and Cha), for casters of another tradition too, and the card says so; the GM asks for the check if the table wants it.
- A scroll is used up (removed at 0 when it auto-destroys, with its row, then bulk is worked out again); a wand spends `uses.value`, which `getWandRecharges` refills at daily preparations, along with its row's uses.
- Staves and coda instruments (GM Core pg. 278; Treasure Vault pg. 136): `getItemSpellKind` is `staff` for the staff trait. At daily preparations (`restWith`'s `finishRest` calls `promptStaffPreparation`, then `promptSpellBlending`), the character picks one staff: it gets charges (`uses.value`/`uses.max`) equal to `getHighestSpellSlotRank` (any prepared or spontaneous entry's highest `numSpellsN`), plus a prepared spell's rank if a prepared caster expends one (`getStaffExpendOptions`, a row not yet used; it's marked used). `getStaffSpells` reads the list from the description (`getStaffDescriptionSpells`: `<li><strong>Cantrip</strong>`/`<strong>1st</strong>` and its spell links) and from its lower versions by name (`getStaffVersionNames`: a greater staff lists only what it adds), and keeps it on the staff (`data.staffSpells` `[{ _id, name, rank }]`); `getStaffPreparationValues` writes it once, with every other staff's charges and spells cleared (charges last a day, one staff a day). Only a prepared staff has rows: `getInventoryItemSpells` gives one per spell and rank (`getItemSpellEntryKey`; `itemSpell.rank`), cantrips in `cantrips`. A cast spends charges equal to the rank (`getStaffChargeValues`; cantrips none) and every row of the staff shows the charges left (`getStaffRowUsesValues`). A spontaneous caster with a slot of that rank or higher left is asked first (`promptStaffPayment`, as `promptSignatureRank` does, then castSpell again with `staffPayment`): the charges, or 1 charge and the slot (`usedSpellsN` of that entry), in the same write. Not enough charges is a line on the card, nothing spent; coda instruments for a non-bard are labelled, not refused. Staff Nexus's makeshift staff and extra expended spells aren't covered.

### GM tools (XP, advancement, initiative, DCs)

`rollhandlers/gm-tools.js`:

- Encounter XP (`getEncounterXp`, used by `onEncounterEnd.js`): the creature table from -4 to +4, or from -7 to +7 under Proficiency without Level (Foundry's `xpVariantCreatureDifferences`). Below the table: 0 XP. Above it: the table's highest. A simple hazard always uses the standard simple-hazard table (2 to 32, as Foundry's `getHazardXp`), and a complex hazard uses the creature table.
- Advancement speed: the campaign setting `advancementSpeed` (standard, fast, slow, milestone) feeds `getXpToNextLevel`. The XP bar's `maxvaluefield` is `data.xpToNextLevel`, which `onLoadCharacter` writes once (`getXpBarValues`). Story milestones return 0 XP, so Level Up always shows (it confirms), and the XP bar hides.
- Initiative:
  - A hazard rolls Stealth (`getInitiativeSkill`). Its Stealth modifier is `data.stealth.value`, which the converter copies from Foundry's `system.attributes.stealth.value` (`getHazardStealthMod`, used in `rollSkill` and the NPC sheet). The DC is that plus 10.
  - An adversary that ties a PC goes first. The tracker sorts on `data.initiative` alone, so `initiative.js` stores an enemy's roll plus 0.1 (`getInitiativeValue`). The roll's metadata says which tokens are adversaries; a roll from a sheet uses the sheet's token faction (`api.getToken()`) when there is one.
- Threat (H21): `getEncounterBudgets(partySize)` (GM Core Table 10-1: 40/60/80/120/160 for four, adjusted 10/20/20/30/40 per character), `getEncounterThreat` (the highest budget reached, Trivial below Low, Beyond Extreme past Extreme) and `getEncounterThreatSummary(tokens)` (party level and size from the non-enemy characters, `getEncounterBreakdown` for the enemies). `onEncounterEnd.js` uses them for its card. Nothing is posted when an encounter starts: the panel's meter shows the threat before the fight.
- Encounter builder (H21): the GM Tools campaign panel (`settings.otherSettings.campaignPanel`, `gmOnly`, `gm-tools-panel.html`, View menu). Its fields are campaign variables: `encounterPartyLevel`, `encounterPartySize`, `encounterCreatures` (`[{ level, type, complex }]`) and `encounterMeter` (`getEncounterBuilderMeter`: one object the panel's labels and progress bar read by path, such as `encounterMeter.threat`, `encounterMeter.budgets.Severe`, `encounterMeter.rows.0.name`; `<label>` ignores `style` and line breaks, so each piece is its own label). The creature rows group the same kind ("2 × Lvl 1 Creature: 80 XP"); the panel has 10, empty ones hidden (`hideifempty`), and past 10 kinds the last is "+N more". Campaign variables reach every client, so no names: a hidden ambush would show. Each `setCampaignVariable` sends the whole map to every client, so an action writes only what it changed plus the meter: a typed level or size only the meter (the field saved itself; the value is passed in), Add Selected Tokens (NPCs and hazards), Add by Level, Remove Last and Clear the creatures and the meter, Use the Party (`api.getParty`) the level, the size and the meter. Add by Level and the templates cover the creature table's range (`getEncounterLevelRange`: -4 to +4, -7 to +7 under Proficiency without Level). The Templates button prompts for a threat (no variable, so the same one posts twice) and posts `getEncounterTemplates` in `[gm]` tags: ways to spend its budget exactly (N of one level, or a leader above the party's level with creatures below it).
- Hazards (H27, GM Core pg. 98): the hazard sheet's Detect button (`detectHazard`, gm-tools.js) rolls each party member's Perception (`api.getParty`, else the characters on the scene) with `api.rollInstant` against the Stealth DC (`getHazardStealthDC`: 10 + `data.stealth.value`) and posts the results as a private message (`api.sendMessage(card, { audience: "private" })`: passing a roll keeps the hazard's name and portrait off it, and players see only "Private GM Message"), each line also in its own `[gm]` tags. The minimum rank comes from `data.stealth.details` ("(trained)", `getHazardMinimumRank`): those below it can't find it, and the card notes that with a rank only those Searching or Seeking roll. The modifier (`getHazardPerceptionMod`) is the sheet's Perception with Perception and Wisdom bonuses and penalties, and Trap Finder against a trap: a circumstance modifier (+2 at master Thievery, `data.thievery` 3+, else +1) inside `mergeModifierLists`, so the module's own Trap Finder modifier (on with the feat's toggle) or another circumstance bonus doesn't stack with it; with a minimum rank the card notes Trap Finder rolls even when not Searching. A Magical hazard gets the Detect Magic line. Disabling is the stat block's own `rollSkillCheck` links in `data.disable`. The module's hazards have no Broken Threshold, and routines aren't counted (no reaction or action tracking, H18).
- DCs: `getSimpleDC(rank)`, `getDCAdjustment` (rarity maps to hard, very hard or incredibly hard) and `getDCForLevel` (PF2e.js). `showDCHelper()`, run from a GM's chat macro, prompts for the skill, the DC and the adjustment. It then posts a roll button for the selected tokens, with the DC in `[gm]` tags.

### Challenges (Victory Points, chases, infiltration, research, Influence)

`rollhandlers/challenges.js` (global script `Challenges`, roadmap B1 and B2, GM Core pg. 184-199) with the Challenges record type (`challenges-main.html`; lists `challenge_obstacle_list`, `challenge_threshold_list`). One record per challenge; `data.challengeType` is victory, chase, infiltration, research or influence, and the sheet hides what the type doesn't use (`getChallengeFieldValues`, written only when it differs).
- Points (`getChallengePointChange`): 2/1/0/-1 by degree for Victory Points, Chase, Research and Influence Points; diminishing Victory Points (`data.scoring`) +1/0/-1/-2; infiltration 2/1 IP, with a failure adding 1 Awareness Point and a critical failure 2.
- Checks: an obstacle's `data.checks` is text as the stat blocks print it ("DC 23 Diplomacy or Society; DC 28 Athletics", `parseChallengeChecks`: a skill without its own DC takes the next one before a semicolon, else the one before). The row's Call button posts a card with a button per check (`getChallengeObstacleMessage`, labelled `Roll_Skill` with no DC, as `getCallForCheckMessage`; the DCs are in the macro code and `[gm]` lines), and an Influence record's Call Influence and Call Discover post its influence or discovery skills with its resistances and weaknesses (`getInfluenceMessage`). A button rolls for the selected tokens (`rollChallengeCheck`, each through `rollNamedSkill`, which vehicles.js shares): a Lore is the creature's own by name, or untrained with Intelligence; Discover passes `action: "Discover"`, one of `SECRET_ACTIONS` (GM Core pg. 187); `metadata.challenge` carries `{ recordId, obstacleId, type, name, obstacle, diminishing, discover }`.
- Results: `skill.js` adds `getChallengeResultLines`: the points and a Score button (`scoreChallenge(recordId, obstacleId, degree)`, GM only), an infiltration failure's Spend Edge Point button (scored as a success, one Edge Point less; refused with none left), and Discover's results in `[gm]`. A diminishing critical success notes it gains 1 VP only if regaining ground is possible. Nothing is scored without the GM: they decide what counts.
- Scoring (`getChallengeScoreValues`, one write from a fresh read): the points go on the obstacle up to its `goal` (Chase Points don't carry over; a research section's goal is its maximum RP), the same change on `data.points`, never below 0. Thresholds (`data.thresholds`, each `{ points, track: points | awareness, outcome }`) passed are posted in `[gm]` lines: going up, or going down with diminishing scoring, where they're drawbacks and reaching 0 VP is a negative event (GM Core pg. 184-185); as is an obstacle overcome and a chase's next obstacle. `data.summary` is the sheet's one line (`getChallengeSummary`: "5 VP", "2 of 6 obstacles overcome", "4 IP, 3 Awareness, 1 Edge", with the round).
- Next Round (`getChallengeRoundValues`) adds 1 to `data.round`, and to an infiltration's Awareness (GM Core pg. 196), with a GM line past `data.roundLimit`. Complete (`completeChallenge`) prompts for accomplishment XP (10/30/80) or an encounter's (80/120) and calls `api.awardExp`.
- Not tracked: infiltration's individual obstacles (each PC's own IP), complications and opportunities (obstacles or notes), per-PC Influence Points, and a chase's pursuers' position. The GM edits the numbers on the sheet.

### Campaign tools (treasure by level, reputation, downtime, connections)

`rollhandlers/campaign-tools.js` (global script `CampaignTools`, roadmap B16, B3, B7). The panel parts follow the encounter builder's rules: campaign variables, each action writing only what it changed plus its meter (`<label>` reads it by path), and the party's level and size are the builder's (`encounterPartyLevel`, `encounterPartySize`): typing them, or Use the Party, also writes the treasure meter (`refreshTreasureMeter`).
- Treasure (GM Core Table 10-9, `PARTY_TREASURE`): `getTreasureBudget(level, size)` follows Different Party Sizes (GM Core pg. 61): for each character past four (or missing), the currency per additional PC, one permanent item of the party's level or 1 higher (`extraPermanent`, shown as "plus 1 × 3rd or 4th") and a consumable at each of those levels. The table has no price for the items, so only the currency changes the total, and the budget line says so. The panel's Treasure section shows `treasureMeter` (`getTreasureMeter`: awarded against the budget, what's left or over, the permanent items, consumables and currency as bare values under the panel's grid headings, and with Automatic Bonus Progression a note to leave out fundamental runes). The section's `<box onload>` calls `loadTreasureMeter`, which writes the meter only when it's missing or differs, so there's no refresh button. `treasureAwarded` is the level's tally in gp: Add Award (`parseGpValue`: "120", "3 gp 5 sp", negative to take back, never below 0), New Level (posts the tally in `[gm]` and starts at 0). Treasure, Reputation and Downtime are `<accordion>`s (campaign variables `treasureOpen`, `reputationOpen`, `downtimeOpen`), so the Encounter Builder stays on top. Awards are typed, not tracked from inventories.
- Reputation (GM Core pg. 200-201): `reputationFactions` (`[{ name, points }]`, -50 to 50) and `reputationMeter` (8 rows, "+N more" past them). Add Faction (at 0, Ignored), Favor or Disservice (+1/+2/+5, -1/-2/-5; posts the new total and any tier change, `getReputationChange`. Table 3-2's `raisedBy` / `loweredBy` on each tier: a change too small for the tier leaves the points and posts that it has no effect), Remove Faction. Faction names reach every client.
- Downtime: the character's `data.downtimeDays` and `data.downtimeLog` (rich text, newest line first) in the Skills tab's Downtime section. Spend Days asks how many and on what, reads the character again and writes both once (`getSpendDowntimeValues`; more than available is allowed, with a note). The panel's Grant Downtime Days adds days to each Party Sheet character (`getGrantDowntimeValues`). Earn Income and the other activities don't spend days on their own.
- Connections (NPC Core pg. 226): the Notes tab's `data.connections` list (`connection_list`: the NPC, the tier from Bonded to Vindictive, notes), set by hand.

### Afflictions (poisons, diseases, curses)

`rollhandlers/afflictions.js` (global script `Afflictions`, roadmap B4, Player Core pg. 430), as Sean laid it out on #64.
- The source: the delivering record's `data.affliction` (an item, an ability record, an NPC's `data.actions` entry, a spell), filled once by `tools/afflictions/fill-afflictions.mjs` from the description: `{ name, kind, virulent, level, save, dc (a number, or "spell" for the caster's), onset, maxDuration, stages: [{ text, note?, damage, conditions, interval }], effectId }`, times as `{ value, unit }` or `{ dice, unit }`. Nothing is parsed during play (`getRecordAffliction` reads the field); a record without it has no Expose button. The parser and report are `tools/afflictions/parse.js` and `report.js` (tested in `tests/test-affliction-parser.js`).
- Expose: `useInventoryItem` and `useAction` add `getAfflictionExposeButton(source)`, which rolls the initial save for the selected tokens (`exposeToAffliction` → `rollSavingThrow` with `options.affliction` and the kind as a trait). `rollSave` copies `options.affliction` into `metadata.affliction` (with the saver's name) and adds `options.extraModifiers`. A spell has no Expose button: `getSpellSaveMacro` passes `{ affliction: { mode: "initial", affliction } }` through `getSaveMacro`'s `extraOptions`, so the spell's one save button (at the caster's DC, with its basic damage) is also the initial save. The parser names a spell's affliction from its bold header (Blood Chestnuts: Draining Growth), else the record's name.
- On a creature, the affliction is its own stackable effect, named as the script names it (`getAfflictionEffectName`, without an ability's "(Graveknight) " prefix): the stacks are the stage (`getAfflictionStage`), its duration the maximum duration (`getAfflictionEffectDuration`: rounds, minutes, hours, days; weeks as days; dice none), so Realm counts it down. Stacks are added one `api.addEffect` at a time with the remaining duration and unit (`getAfflictionStackDuration`): `api.addEffects` ignores durations, and a stack added without one drops the unit (checked live). Removing stacks (`deductEffectById`) keeps the duration.
- What the effect can't hold is `data.afflictionState` on the token, shown as the Afflictions list (`affliction_list`, `affliction-list.html`) on characters' Notes tab and NPCs' Description tab. Rows are `{ _id, name, data: { affliction, appliedStage, onsetLeft, roundsLeft, successes, tickRound, ended, summary } }`; `getAfflictionStates` reads them flat and `writeAfflictionStates` writes them back as rows with `summary` (`getAfflictionSummary`) worked out, through `api.setValuesOnTokenById(creature._id, creature.recordType, ...)`. Each row has Save (`rollAfflictionSaveFromRow`, the GM's way to roll an hour or day interval's save), Apply Stage (the stage the effect's stacks show) and Remove (`removeAffliction`: the effect, the stage's non-lasting conditions and the row; the Clear chat button calls it too). The buttons act on `api.getToken()`. An entry whose effect is gone never blocks a new exposure (`getAfflictionExposure` replaces it, keeping its `appliedStage` so the swap takes its conditions off), and a stage change or the effect coming back clears `ended`.
- Save results (`getAfflictionSaveLines`, save.js): the initial save's degree (not afflicted, a spell's own success left to its text; stage 1, or 2 on a critical failure, after any onset) with Apply (`afflictCreature`: new state and stacks; a poison again raises the stacks keeping the duration; a curse or disease it has, nothing; with an onset the stacks go on and the conditions wait). A spell's affliction keeps the cast DC as `castDC` for its stage saves. A stage save (`getAfflictionSaveChange`: -2/-1/+1/+2, virulent two successes for -1 and a critical success -1, capped, below 1 cured) has Apply (`resolveAfflictionSave`: the Treat effect of that kind comes off first, and the rest waits for that write; then from the effect's stacks, so a GM edit counts): a virulent success that doesn't reach a stage writes only the count and the next interval; anything else `setAfflictionStage`.
- Stages (`setAfflictionStage`, pure part `getAfflictionStageValues`): one write of the state; the effects in one chain (`applyAfflictionEffects`): removals first (the affliction's stacks, then conditions by `deductEffectStacks`), then the conditions added in one `api.addEffects` (new ones through `addConditionGain`), then the stacks; and a card with the stage's text, its note in `[gm]`, and damage buttons. Conditions swap per `getAfflictionConditionChanges`: drained, doomed, frightened, sickened, fatigued, wounded and stunned are only gained, never removed. The highest stage repeats; below 1 the effect and state go.
- Turn end (onTurnEnd.js, `runAfflictionTurnEnd`, pure part `getAfflictionTurnEnd`): once a round (`tickRound`), counted onsets and intervals (rounds, minutes as 10 rounds) go down by 1, posting Apply or Roll_<Save> (`rollAfflictionSave`). An affliction whose effect is gone (the GM removed it, or its duration ran out) gets one Clear button (`clearAfflictionState`, which is `removeAffliction`). Hours and longer are the GM's, with the row's Save button.
- Treat Poison and Treat Disease (skill.js, `getAfflictionTreatmentLines`): Apply_Treat_Poison or Apply_Treat_Disease applies the Player Core effect (`applyEffect`), whose choice gives +4, +2 or -2 and whose `saveBonus-circumstance` rule has the `item:trait:poison` (or disease) predicate; the stage save's Apply removes it.
- Not tracked: a poison applied to a weapon (the GM posts Expose when the Strike hits), blighted boons, and stage effects other than damage and conditions (in the stage's text).

### Travel and the environment (hexploration, weather, falling)

`rollhandlers/travel.js` (global script `Travel`, roadmap B5 and B6), two accordions on the GM Tools panel after Downtime. Campaign variables as the encounter builder's: `hexState`/`hexMeter` and `weatherState`/`weatherMeter`, each action writing the state and the meter its labels read; the sections' `<box onload>` calls `loadTravelMeters`, which writes a meter only when it differs.
- Hexploration (GM Core pg. 207): `getHexActivitiesPerDay` (Table 3-6, ½ at Speed 10 or less) from the slowest Party Sheet Speed (`setHexSpeedFromParty`, `getCreatureSpeed` reads `data.speed` or `data.speed.value`). Start Day (`getStartDayValues`): the day's activities, a forced march's extra Travel (a full one at Speed 10 or less), with a `[gm]` line of each PC's safe days (Constitution modifier, minimum 1) and the rule; its days aren't counted, and the GM applies fatigue, and the encounter flat check (`getHexEncounterCheck`: Table 3-7's DC by region, -2 road or river, +3 flying; critical success two encounters; Table 3-8's type by 1d10). The dice are `Math.random`, posted in `[gm]`. Travel and Reconnoiter (`getHexActivityValues`): the hex's cost by terrain (open 1, difficult 2, greater difficult 3; a road one step better for Travel), spent from the day's activities, the rest carried in `task` to the next activity or day (shown with `formatAmount`, ½ for half). A forced march day refuses Reconnoiter (Travel is the only activity), and switching kinds drops the unfinished task with a line saying so. The prompts' answers go through the file's one `pick`. Travel Time (`getTravelTime`): a Speed's tenth in miles per hour, 8 hours a day, ½ and ⅓ for difficult terrain (Player Core pg. 438).
- Weather (GM Core pg. 95): Set Weather prompts temperature (`TEMPERATURES`, with fatigue hours, damage and the cold-weather gear note in `gear`), then precipitation, fog and wind as none to severe (-1 to -4 circumstance). `getWeatherMeter` gives the summary, the fatigue hours (4 with precipitation heavier than light), the damage line and up to three effect lines. The GM's calls in the book (fog concealing, flying in wind as difficult or greater difficult terrain, strong wind calling for Athletics) say "can", not tied to a severity. Announce posts it. Temperature Damage and Environmental Damage post the category's low and high rolls (Table 10-11) as `executeDamageMacro` buttons.
- Falling (Player Core pg. 421, `getFallDamage`): half the distance over 5 feet, up to 1,500 feet, less 20 feet for water or snow or 30 diving in (the GM checks the depth). The card has the damage, Apply_Prone and the DC 15 Reflex amounts for landing on a creature.
- Not covered: Kingmaker's weather and camping (the Kingmaker module), individual hexploration activities (rolled from the sheets), and tracking which hexes are explored (the map's fog of war).

### Vehicles (piloting, Run Over, collisions)

`rollhandlers/vehicles.js` (global script `Vehicles`, roadmap B9, GM Core pg. 210-213), a Vehicles accordion on the GM Tools panel after Weather and Environment. Vehicles are NPCs with `data.type` "vehicle" (their stat fields are on npcs-main's vehicleProperties box); nothing is added to their sheet, and nothing is kept between cards.
- Vehicle Card (`postVehicleCard`): for the selected vehicle token, after the GM picks the terrain (`VEHICLE_TERRAIN`: difficult a hard DC, +2; greater difficult incredibly hard, +10). `getVehicleInfo` reads `pilotingCheck` ("Arcana (DC 32), …, or Piloting Lore (DC 30)", `parsePilotingChecks` through `parseChallengeChecks`), the first Speed in `speed.details`, AC and `collisionDC`/`collisionDamage`; broken (`curhp` at or below `brokenThreshold`, else half the HP) adds +5 to the piloting DCs, halves the Speed and takes 2 from AC and the collision DC. The card (`getVehicleCardMessage`) shows the skills without DCs (the DCs in `[gm]` and the buttons), the momentum rule (Drive, Run Over or Stop each round), and buttons carrying the vehicle as posted: Drive (1, 2 and 3 actions), Run Over and Take Control (`pilotVehicle(key, vehicle)`), Stop and Board. The GM reposts it when the terrain or the vehicle changes.
- Piloting (`pilotVehicle`): for each selected token, the skill the player picks when there's more than one, rolled with `rollNamedSkill` and `getPilotingMetadata` (the action and its traits, move and reckless or manipulate; Drive 3's -5 in `extraModifiers`; `metadata.vehicle` `{ action, name, speed, size, collisionDC, collisionDamage }`). Board prompts whether it's moving: no check, or Acrobatics or Athletics against its AC.
- Results: `skill.js` adds `getVehicleResultLines` (`VEHICLE_ACTIONS`): Drive's three outcomes (a critical failure uncontrolled), reckless actions' failure (Speed in a straight line, the GM's 45-degree drift, uncontrolled), Drive 2 and 3 at twice and three times Speed, Run Over at twice Speed through creatures two sizes smaller and a ram of one target one size smaller or larger (no upper limit), with the collision's basic Reflex save and damage (`getCollisionLines`; "9d10" is bludgeoning; the DC only in a `[gm]` line and the button's code, as the piloting DCs) for Run Over and an uncontrolled vehicle, and the attack penalty from it (-2, -4 after a reckless action or uncontrolled).
- Collision (`postVehicleCollision`) posts a crash's save and damage for the selected vehicle.
- Not covered: moving the token, the uncontrolled vehicle's slowing each round, initiative by piloting skill, and AC and save penalties on the token while broken (the GM's).

### Inventory tools (effects on Use, selling, investiture, handwraps, Bulk)

`rollhandlers/inventory-tools.js`:

- Effects on Use: `useInventoryItem` adds Apply buttons (`getEffectMacrosFor`) for `getItemUseEffects(item)`. Those are the item's own `data.useEffects` (the "Effects on Use" multiselect on the Rules tab) plus every effects `<record-link>` in its description, which is how the modules link "Effect: Bestial Mutagen (Lesser)".
- Selling: `sellInventoryItem(itemDataPath)` is the row's coin button and the grid's Sell action.
  - Both are hidden, and `sellInventoryItem` does nothing, unless the campaign setting "Allow Selling from the Sheet" (`sellFromSheet`, default No) is Yes. `setItemFields` sets `fields.sellBtn.hidden`, and the Inventory tab's onload (`onInventoryLoad`, `getSellButtonValues`) brings every row in line after the setting changes.
  - An item sells for half its Price per unit (the Price is per bundle, `getItemBundleSize`). Treasure sells for its full Price. The total is rounded down, not each unit (`getSellTotalCp`): 10 arrows sell for 5 cp.
  - Shoddy, temporary and infused items get a note in the confirm, not a block.
  - It reads the record again, writes the coins and count in one `setValues`, then removes a sold-out row by its id (`removeValueFromRecord`) and recalculates.
- Investiture: `data.investedCount` is set in the recalc (`getInvestedCount`). It counts items with the invested trait, and armor with runes, that are invested. Investing an 11th (`getInvestmentWarning`) or using an uninvested item that needs it (`getUninvestedUseWarning`) shows a notification. Nothing is blocked.
- Handwraps of mighty blows: an item named so, or with `data.handwraps` ticked, worn (`carried: equipped`) and invested, lends its potency, striking and property runes to every other unarmed attack.
  - `withHandwrapsRunes` is applied first in `getAlteredWeapon`.
  - `getEffectsAndModifiersForToken` also lets the handwraps' item-only modifiers (their property runes' features) apply when `itemId` is an unarmed attack (`getHandwrapsItemIdFor`).
  - The handwraps' own attack is left as it is, and NPCs are skipped.
- Bulk: `data.bulk` is "encumbered above" (5 + Str + `bulkLimit`), and `data.maxBulk` is 10 + Str + `bulkLimit`.
  - `updateTotalBulk` drops fractions (`dropBulkFractions`: 12 light items are 1 Bulk).
  - Crossing a limit posts a chat card (`getEncumbranceMessage`), with an Apply_Encumbered button when the character becomes encumbered. It's posted only for changes the user made: `updateTotalBulk(record, true, true)` (adding, removing, using or selling an item, coins, a count). The tab's onload never posts it.
  - `speedPenalty` (untyped) and `speedPenalty-circumstance`/`-item`/`-status` effect types exist. Foundry's Encumbered is an untyped -10 to all Speeds plus Clumsy 1.

### Healing tools (Treat Wounds and Battle Medicine, persistent damage, rest, regeneration)

`rollhandlers/healing-tools.js`:

- Treat Wounds and Battle Medicine: `treatWounds(kind)` runs both (`battleMedicine()` is `treatWounds("battleMedicine")`, the button on the Battle Medicine feat's card).
  - The metadata's `treatWounds` carries `kind`, `healerId` and `healerName`. The healing adds the module's "Treat Wounds Immunity" (anyone's, 1 hour) or "Battle Medicine Immunity" (that healer's, 1 day) with the healer as applier (`applyMedicineImmunity`). Every result card also has an Apply button for it, safe to click again.
  - A patient already immune gets a warning before the check (`getMedicineImmunityWarning`). Nothing is blocked.
  - Battle Medicine's healing passes `treatWounds: false`, so wounded stays.
  - Several instances of an effect: `effectIds` repeats the id, and `effectValues[id]` becomes an array of `{ value, tokenId, tokenName }` (`getEffectInstances`).
- Persistent damage:
  - `applyPersistentDamage` keeps the higher of one type (`getPersistentStackChange`, by average): a lower or equal one isn't added, and a higher one replaces it (`removeEffectById` with `instanceIndex`).
  - The recovery check: `getPersistentRecoveryOutput` gives the Roll_Recovery button, or rolls it now with the setting "Persistent Damage Recovery" (`persistentRecoveryRoll: auto`), plus an Assisted Recovery button at a flat DC 10 (particularly appropriate help). `flatCheck.js` finds the token by `metadata.tokenId` for an automatic roll.
  - Healing to full Hit Points ends persistent bleed (`applyHealingToToken`, `endPersistentBleed`).
- Rest: `rest()` asks first (`showRestOptions`: one choice, a normal night's rest first, and a days prompt only for long-term rest), then runs `restWith(options)`.
  - No shelter halves the healing (minimum 1). Each long-term rest day heals double (`getRestHealingAmount`). Sleeping in armor without the comfort trait wakes the character fatigued (`isRestFatiguing`).
  - The chat line reminds the GM to advance the calendar. `showWatchOrder()` (a GM chat macro) posts the party's watches (GM Core: 8 h x n / (n - 1)).
- Fast healing and regeneration (`getSelfHealing`): a monster's from `hpDetails` or an ability's name, and any creature's `fastHealing` modifiers and effect rules (characters too; the highest value, a formula allowed):
  - Never automatic: only the GM knows whether regeneration was deactivated (damage types, materials, traits). `onTurnStart` posts a card ("Regeneration 20 (deactivated by electricity or fire), unless deactivated.") with an Apply Healing button that calls `applyHealingToToken`. No card at full Hit Points, and once per round (`data.selfHealRound`).
  - At 0 HP a regenerating monster is dead as any NPC, with a Regeneration button (`useRegeneration`): Dead off, dying (at most 3), unconscious and prone.
- Ferocity (an NPC ability named so): a button at 0 HP until wounded 3. `useMonsterFerocity` sets 1 HP and wounded + 1, and removes the Dead or Unconscious the damage added.

### Spells (heightening, damage rows, casting time)

`rollhandlers/spells.js`:

- Interval heightening adds each step to the damage row of the same index, in that row's category: Blood Vendetta's persistent 2d6 bleed is 4d6 persistent at 4th. A step of the same die and type adds up ("4d6"); another die or type is its own term.
- Fixed heightening applies every rank up to the casting rank, lowest first, each over the last (Telekinetic Hand at 5th keeps 3rd's target). A rank without damage keeps the earlier damage. Target, range and duration may be text or the converter's `{ value }` object (`getHeightenedText`).
- A damage row can carry `data.predicate` (JSON text, as a modifier's). Such a row isn't in the spell's damage: `calculateSpellDamage` returns it in `targetDamage` (`{ value: "7d6 spirit", category, predicate }`, heightened like any row), and the damage and attack buttons ask `getSpellTargetDamage` when rolled: on against a single target the predicate passes for, offered unticked ("Chilling Darkness (vs holy)") with no target or several, left out when it fails. A persistent row is added only when the predicate passes (it can't be ticked). Splash rows ignore the predicate.
- A defense whose attack and save statistics are both empty is no defense, so the spell gets its damage button.
- Damage and healing cards carry `damageSource` from `getSpellDamageSource`: the spell's slug (an overlay's is its spell's: Heal (vs. Living) is heal) and `castRank`, so healingReceived rules see `item:slug:heal` and `@spell.rank` (Angelic Halo), on the healing card and in applyDamage's vitality healing.
- Casting times longer than actions (1 minute, 10 minutes, 1 hour) are kept: the sheet clears `data.actions` and hides the icon, and the card shows the time as a tag. "2 to 3" is `twoToThreeActions`.
- Description damage buttons (`executeDamageMacro`) work their math out first (`resolveDamageFormulaMath`): `(@item.level -3)d6`, nested `floor`/`ceil`/`min`/`max`, `ternary`, `{...}` and products, rounded down at the end.
- AC knows a spell attack's or Strike's range (`getArmorClassForToken`'s `extraContext.attackRange`): `origin:item:melee` or `origin:item:ranged`, for "+2 AC against ranged attacks".
- An effect rule whose predicate fails only on atoms the roll can't know (the action, target, effect source or terrain) is offered as an unticked opt-in named for what it's against ("Spell Effect: Safe Passage (vs hazard)"), as a feature modifier's is (`SITUATIONAL_MODIFIER_TYPES`, the type without its -status/-circumstance/-item suffix).
- Effect rules of type `adjustDegreeOfSuccess` work as a feature modifier's: the adjustment in `data.adjustment` or the value (`{ "success": "one-degree-better" }`, an object or JSON text), the field the statistic.

### Spell pickers (H2 phase C)

`rollhandlers/spell-pickers.js` fills the empty rows the managed spellcasting entries make (spell-entries.js), so spells needn't be dragged in. `getOpenSpellRowGroups` lists them per entry and rank: managed entries only (`isPickableSpellEntry`: not focus or item entries, not `autoSlots` off or `auto.orphaned`), and not one still waiting on its tradition (a sorcerer before the bloodline) except the Divine Font. `getSpellPickGroups(record, levelUp)` is what's offered: books first, then slots. `promptSpellPicks(recordId, next, levelUp)` reads the record again before each group and prompts once per group for up to `count` spells, writing each group in one `setValues`; a skipped or partly filled group isn't asked again (the `done` keys are passed along, no module state).

- **Spontaneous:** the query leaves out only the spells already in that rank's list (`getRankSpellNames`): a repertoire can hold a spell at more than one rank (Player Core pg. 297).
- **A book** (`getSpellbookRules(entry, record)`, the `spellbook` of the class's edition via `getClassSpellcasting`: the wizard's and magus's spellbook, the witch's familiar; not a cleric or druid) is the entry's Available Spells (`knownSpells`). At 1st level (the creation wizard, 1st level from level 0) it's asked for what it starts with and lacks (10 cantrips and five 1st-rank spells for a wizard; a magus 8 and 5, 8 and 4 in Secrets of Magic); at Level Up for the level's `perLevel` new spells, of any rank with slots. A remastered wizard's school curriculum isn't in the repo: the prompt says to drag its spells in (two at 1st level, one when a new rank arrives), and the 1st-rank count leaves room for the two. Picks are appended as copies with new ids (`getSpellbookValues`); the book's names are left out of the query. Archetype books (Basic Wizard Spellcasting) are left to the wand.
- **Prepared slots:** not at Level Up (they're prepared at daily preparations). At 1st level a book's slots are prepared from the book (`getKnownSpellOptions`, as the wand does) and wait for the wand while it has none of their rank; a cleric's or druid's come from the compendium. Their prompt passes `showPrompt`'s `allowRepeats` (`canRepeatSpellPicks`: prepared slots of 1st rank and up, more than one), so a spell picked again fills another slot; a repertoire, a book and cantrips don't.
- **Divine Font** (`auto.source` ending `:font`): its rows all get heal or harm, at 1st level and at Level Up: the font the class feature chose (`auto.spellFilter`), or the player picks one. One record per name, the remastered one when the compendium has both (`getRemasterSpellsByName`).

Rarity isn't filtered (the GM's call), as the wand's list. Hooks: the last step of Level Up (`levelUp` true) and of 1st level from level 0 (`characters-main.html`, before the final pass, whose `processChoices` prompts would otherwise open at the same time; an archetype entry from a feat taken in the same Level Up gets its rows in that final pass, so it's left to the wand), and the creation wizard's Spells step (`wizards/characters/spells.html`, `getOpenSpellRowsSummary`). The spell list's drop and wand use the same row and query (`buildFilledSpellRow`, `getSpellSlotQuery`, `getSpellDefenseString`).

### Check tools (Assurance, incapacitation, signature spells, counteract, condition flat checks)

`rollhandlers/check-tools.js` (global script `CheckTools`), with the `counteract` roll type (`rollhandlers/counteract.js`):
- Assurance: `rollSkill` asks "Roll the check / Use Assurance (N)" for a character's skill with Assurance (trained or better). The skill comes from the feat's name ("Assurance (Athletics)") or its choice (`data.choices[i].data.choices[0]`). An Assurance with neither asks once which skill it's for (the current one first) and keeps it as the feat's choice (`getAssuranceSkillValues`); "Not now" rolls and asks again next time. The fixed result (10 + `getProficiencyBonusForRank`) goes to `skill.js` through `api.roll`, so the DC, notes and degree adjustments still apply. Not for initiative, Perception or NPCs.
- Untrained Improvisation has no code: the module feat's `skillBonus` modifier (predicate `proficiency:untrained`) already adds it on untrained rolls. The sheet's skill modifier stays ability + proficiency, as for every other modifier.
- Incapacitation: `getSpellSaveMacro` passes the casting rank (`rank` in the save options) for an incapacitation spell. `rollSave` sets `metadata.incapacitation` when the saver's level is more than twice that rank (or, with `level`, higher than the effect's level). `save.js` makes the result one degree better after every other adjustment. A spell attack does the same per target (`metadata.incapacitation` from `getSpellAttackMacro`): `attack.js` makes it one degree worse.
- Signature spells: a Signature checkbox (`data.signature`) on spontaneous spell rows, hidden by default. Every row builder sets `fields.signatureBox`, and the spells list's onload (`getSignatureBoxValues`) writes only the rows that differ. `castSpell` first asks for the rank (its own up to the highest with a slot left; also when the only rank left isn't the list's), then casts again with `spell.castRank`, which `getCastingRank` returns ahead of the list's rank.
- Counteract: a spell whose text mentions counteracting gets a Counteract button (`counteract(name, rank, mod)`). It asks the DC, then the target's rank (a targeted creature's half level first), then rolls a check (not an attack roll, as Foundry's counteract statistic): the entry's modifier plus `allBonus`/`allPenalty` for the casting attribute and the `counteract` field (`getCounteractModifiers`). The button carries the caster's token id, so an unlinked NPC's conditions count; the record is read only when the token isn't on the scene. `getCounteractOutcome` is the Player Core table.
- Flat checks to cast (`rollCastingFlatChecks`, after the spell's card): stupefied (DC 5 + value), grabbed for a manipulate spell, deafened for an auditory one (DC 5). `flatCheck.js` adds `metadata.failureNote` on a failure. Nothing is undone.
- Sickened: `retch()` rolls Fortitude against a typed DC (`metadata.retch`), and `save.js` adds a Reduce Sickened button on a success (2 on a critical success). `useInventoryItem` warns about a potion, elixir or ingested item while sickened.
- Confused: `applyDamage` adds a DC 11 recovery flat check button, not for persistent damage. `flatCheck.js` removes `metadata.endsCondition` from the token on a success.

### Combat riders (monster Strike riders, recharges, Debilitating Strike)

`rollhandlers/combat-riders.js` (global script `CombatRiders`):
- Effect durations: "until the end of <applier>'s next turn" is `api.addEffect(name, token, { value, unit: "end_applier_turn" }, { value, _id, name })`. The value counts the applier's turn ends (checked live): 2 on the applier's own turn, 1 on someone else's (a reaction; `getEndOfNextTurnValue` reads the attack log's current turn). The 4th argument records the applier.
- Strike riders (Monster Core): `performAttackRoll` puts `strikeRiders` (`getStrikeRiders`: the module's `attackEffects` names, or the editor's slugs) in the metadata. On a hit (or with no DC), `attack.js` adds each rider's text and a roll button (`rollStrikeRider`). It runs the monster's `performSkillAction(monster, "athletics", "Grapple" | "Trip" | "Shove", true, { targetId, noMultipleAttackPenalty })` against the Strike's target, so the maneuver card's outcomes and Apply buttons follow. Grab, Knockdown and Push (and their Improved versions) neither apply nor count toward the multiple attack penalty. A listed Trip is the monster's own Trip, with the penalty. Constrict is its own NPC action, with its buttons in the module data.
- `performSkillAction` options: `targetId` (a given creature instead of the targeted one) and `noMultipleAttackPenalty` (no penalty options, and not logged as an attack).
- Recharges: `useAction` adds a Start Recharge button when the text says the ability can't be used again for N rounds (`RECHARGE_PATTERN`: "can't use", "can't <Ability>", "cannot", "can't be used", and formulas like 1d6+1; `getRechargeFormula` reads a button's label). `startRecharge` rolls with `api.rollInstant` and, in combat, keeps `{ name, readyRound }` in `data.recharges`. `onTurnStart` tells the GM (`[gm]`) when the round comes and removes the entry. `onEncounterEnd` clears them (`clearEncounterRecharges`).
- Debilitating Strike: `debilitation` in the metadata (`getDebilitationCount`: the "debilitation" toggle, 2 with Double Debilitation), with `debilitationDuration` (1 off the rogue's turn) and `debilitationFeats`. A hit on an off-guard target lists the debilitations, with an Enfeebled 1 button until the end of the rogue's next turn. The Speed penalty has no module effect yet, so it's listed only.

### Weapon traits, hands in use, firearm loading

`rollhandlers/weapon-traits.js` (global script `WeaponTraits`). Rules follow Foundry PF2e.
- Kickback and jousting: `getWeaponTraitModifiers(record, weapon, { isNPCAttack, damageDice })` returns `{ attack, damage }`, used by `performAttackRoll` (next to the momentum traits) and `performDamageRoll`. Kickback: +1 damage, and a -2 circumstance attack penalty, unticked with Strength +2 or more (a stabilizer: the player unticks it). Jousting: a circumstance bonus equal to the damage dice, offered unticked (mounted, moved 10+ feet). NPCs get neither (their damage already has kickback's 1).
- Concussive: `applyDamage` looks up type immunity and resistance under `getConcussiveProtectionType(IWR, type, traits)`, the weaker of piercing or bludgeoning (immunity counts as the most). Weaknesses and physical or all-damage resistance are unchanged. Backstabber was already in `applyTargetOffGuardDamage`.
- Parry: the attack row's Parry button (`parryBtn`, shown for the trait) adds the module's Parry effect (`parryWithWeapon`). Untrained is a GM-only note, not a block.
- Versatile with any damage type: a weapon with a versatile trait other than B, P or S (`hasOtherVersatileType`) shows the `versatileType` dropdown (`getVersatileOptions`) instead of the checkboxes; `getWeaponDamageInfo` uses `getVersatileDamageType`.
- Hands: `getHandsHeld(item)` (equipped and held: 2 for two hands or a 1+ weapon on its two-hand button, else 1; worn, carried and unarmed are 0), `getHandsInUse(record, changes)` `{ held, free, reallyFree }`. Roll options `hands-free:<n>` (shields and free-hand weapons don't count) and `hands-free:but-really:<n>`, as Foundry's. Each held weapon adds `self:weapon:melee` or `self:weapon:ranged` and `self:weapon:hands-held:<n>` (`getHeldWeaponAtoms`; Inexorable Iron's melee weapon in two hands). `data.handsLabel` ("Hands n/2", Actions tab, shown only past 2: `fields.handsLabel.hidden`) is written by `getHandsValues` (only on a change) from `onAddEditFeature`, `onItemEquippedFor`, Stow, Drop, Draw and the hand button. More than 2 is a notification (`noteHandsInUse`), never a block.
- Loading: `getLoadCapacity`, the one place that says how many loads a weapon holds, as Foundry's `ammo.capacity` (1 for a weapon fed by a magazine: repeating, or ammo with `uses.max` > 1; else capacity N, 2 for double barrel, else 1), `getLoadedCount` (`data.loadedCount`; one shot when only `loadedAmmo` is set). Reload (`reloadWeapon`, `getReloadValues`) loads one up to the capacity; a shot (`getShotValues`) uses one, or two for both barrels, which expend `max(2, expend)` as Foundry's (`data.doubleBarrel`, `isFiringBothBarrels`, which steps the damage, striking and fatal dice up: `stepUpDie`). Only one barrel loaded: a note, and one fires. The card's `reloadNote` (attack.js) says what's left, and for a repeating weapon whose magazine ran out, that a new one takes a free hand and 3 Interact actions (`getMagazineNote`).

- Overdrive (Guns & Gears pg. 16): `useAction` rolls Crafting against `getDCForLevel` (`getOverdriveUse`) with a `targetNotes` note per result: the module's Overdrive (Critical Success), (Success) or (Failure) effect to apply (the first two noting the 1-minute lockout when it ends), and on a critical failure the half-level fire damage and a 1d4-round `startRecharge` button. Unstable actions: `useAction` rolls the DC 15 flat check (13 legendary in Crafting) with `api.roll` as a `flatCheck` (`getUnstableUse`), its `failureNote` the malfunction and its `criticalFailureNote` the half-level fire damage; retuning isn't tracked. `attack.js` changes a d20 in the roll's `rollString` `@(...)` values too (`setD20InRollString`), since the card draws its dice from them.
- Exploit Vulnerability (Dark Archive pg. 32; the action and its toggles, the Exploit Vulnerability effect and Esoteric Lore are the Dark Archive module's records): `useAction` rolls Esoteric Lore (the character's `Esoteric Lore` lore skill: its rank, and its mod when it has an attribute picked; the module's grant sets none, so `getEsotericLore` works it out with Charisma) against `getDCForLevel` of the target's level (`getExploitVulnerabilityUse`), with notes per result: what it learns in `[gm]` tags (all IWR on a critical success, the highest weakness on a success; `getExploitIWR` over `getIWR`), Exploit buttons for mortal weakness and personal antithesis (antithesis only on a failure), and Off-Guard until the next turn on a critical failure. `exploitVulnerability(thaumaturgeId, targetId, mode)` takes the last exploit's effect off its target (`data.exploit` `{ targetId, mode }` on the thaumaturge), adds the module's Exploit Vulnerability effect (a `tokenMark`) with the thaumaturge as `tokenId`, and turns on the action's matching toggle (`exploit-vulnerability:personal-antithesis` or `:mortal-weakness`, the other off) in the same write. Off-Guard on a critical failure also calls `exploitVulnerability(thaumaturgeId)` with no mode: the last exploit's effect comes off, both toggles off, `data.exploit` null. Both exploits are weaknesses (added once, after a critical hit's doubling): `performAttackRoll` adds `getExploitDamageCategories` to a target's damage categories (magical, and with the Mortal Weakness toggle on, the target's highest weakness; `applyDamage` matches weaknesses against categories) and puts `getExploitWeakness` (2 + half level with the Personal Antithesis toggle on) in its metadata as `exploitWeakness`; attack.js carries it to the damage roll, and `applyDamage` counts it in the highest-weakness choice for one damage type. Same-type creatures for a mortal weakness are left to the GM.
- Unleash Psyche (Dark Archive pg. 12): `useAction` adds the module's Unleash Psyche effect (2 rounds; `spellDamageBonus`/`cantripDamageBonus` status `{2*@spell.rank}`) unless stupefied or its `data.recharges` wait isn't over (`getUnleashPsycheUse`). `onEffectsChanged` posts `getPsycheSubsidesMessage` when it ends, with one button for stupefied 1 (2 rounds) and the 2-round wait (`startRecharge`): the hook can't add effects to the same creature.
- Drain Bonded Item (Player Core pg. 197): `useAction`'s card adds `getDrainBondedItemUse`, a Cast a Spent Spell button (`castSpentPreparedSpell(recordType, recordId)`, by the character's id) that prompts for a prepared spell already cast today (`getSpentPreparedSpells`) and casts it with `castSpell`, which marks a prepared row used again and never refuses. Once a day is the action's frequency (limited-uses.js).
- Spell Blending (Player Core pg. 195; the thesis by `data.flags.arcaneThesis` or the feature's name, `hasSpellBlending`): at daily preparations `promptSpellBlending` undoes the entry's last trades (`data.spellBlending` `{ trades: [{ from, to }], cantrips }`, `undoSpellBlending`), then offers trades one at a time until Done (`getSpellBlendingOptions`: two slots of a rank for one up to 2 ranks higher, at most the highest rank the entry has and each bonus rank once; one slot for two cantrips, once) and writes the counts that changed and the trades once (`getSpellBlendingValues`). The entry is the class's (`auto.source` `class:wizard`) or an arcane prepared one. A count above or below its base is the player's own change, so the class sync keeps the trades for the day.
- Granted lore skills keep the proficiency's attribute (`updateProficiencies`: a lore proficiency's `ability` goes on the new lore skill, or an existing one without one).
- Necromancer Refocus (Grave Spells, Impossible Magic pg. 27): a necromancer (the class, Grave Spells or the archetype's Necrotic Bomber: `canDestroyThrallToRefocus`) with 2 or more Focus Points spent is asked whether they destroy a thrall (`promptRefocusOptions`, spell-entries.js); yes gives back 2 (`getRefocusPoints(record, { destroyThrall })`) and the card says so. Thralls aren't tracked: the player says they have one and removes its token.

`rollhandlers/armor-traits.js` (global script `ArmorTraits`), following Foundry's character prepareSkills, prepareSaves and createPonderousPenalty.

`rollhandlers/familiars.js` (global script `Familiars`). A familiar is an NPC of type familiar; its abilities are its actions with `actionCategory` familiar.

`rollhandlers/summons.js` (global script `Summons`), with `rollhandlers/onTokenAdd.js` (the combat tracker's onTokenAdd).

The Notes tab's companion box (master field, Match Master's Level) shows for eidolons too and links one to its summoner (`data.companionMaster`); the summoner links back (`data.eidolon`), as a familiar's master does.
- `syncEidolonWithSummoner`: the summoner's level, maximum, current and temporary HP in one write, then the summoner's link if missing; the sheet is worked out again when the level changed.
- Shared Hit Points (Impossible Magic pg. 63): `shareHitPoints(creature, values)` copies `data.hitpoints`, `data.curhp` and `data.tempHp` just written to an eidolon or its summoner to the other, reading it fresh and writing only what differs (dying and wounded aren't shared). It's called by applyDamage (common.js), damageScript.js, healingScript.js and dying.js's healing; a summoner's new maximum in `updateAttribute` goes to its eidolon, and a linked eidolon's maximum isn't recomputed.
- An eidolon goes just after its summoner in initiative through the companion master link (summons.js).
- Gear (Impossible Magic pg. 70): `getSummonerGear` snapshots the summoner's armor potency, resilient rune or bands of force, and worn, invested handwraps into the eidolon's `data.summonerGear` (on sync, and when the summoner's sheet works out its Hit Points: `shareSummonerGear`). `getEidolonGearModifiers` (called beside `getAbpModifiers`) adds the AC and save bonuses, and `getWornHandwraps` returns the summoner's handwraps for an eidolon, so their runes go on its unarmed attacks. Nothing with Automatic Bonus Progression.
- HP is also shared by temporary HP from actions and the healing card, Orc Ferocity and Undying Ferocity, and Rage's end. A linked eidolon's Rest heals nothing (the pool is the summoner's; restWith's `sharesPool`).
- 0 HP (Manifest Eidolon, pg. 64): a linked eidolon brought to 0 by applyDamage or the tracker's damage script gets no dying of its own; `applyEidolonZeroHitPoints` runs `getZeroHitPointsChanges` on the summoner's token (dying, 2 on a crit; the conditions) and the card says the eidolon unmanifests. A summoner at 0 gets the unmanifest line too. The damage card's Undo restores the partner's shared HP and the summoner's dying (`getSharedHitPointUndo`).
- One effect on both (pg. 63): applyDamage keeps a pool per summoner (`sharedPools`, keyed by `getSharedPoolKey` when the partner is among the targets); the second of the pair starts from the pool as the first left it and takes only what its amount adds (`getSharedPoolDamage`), so the greater applies once. Apply by Saves passes one pool for its card (`options.sharedPools`, `options.poolCreatures`).
- Ranks (pg. 69): the sync and the summoner's recalculation snapshot the summoner's ranks into `data.summonerRanks`; `updateProficiencies` takes the skill ranks for every eidolon, and Perception and save ranks too with Summoner Dedication (Eidolon), as exact ranks (`getEidolonSharedRanks`). The Eidolon class features' proficiencies and modifiers carry `{not: feat:summoner-dedication-eidolon}`. The gear snapshot also has the summoner's best item bonus to Perception and each skill from invested items.
- A ranged unarmed attack (Ranged Combatant) uses Dexterity but no ammunition (performAttackRoll's `isRangedUnarmed`).

### Sustained spells (Sustain, turn-end ending)

`rollhandlers/sustain.js` (global script `Sustain`). Casting a spell with `duration.sustained` records it on the caster's token (`data.sustaining`: `{ name, castRound, sustainedRound, limitRounds, limitLabel }`, written with `"tokens"`) and adds a Sustain button to its card (`getSustainButton`, `startSustainingSpell` in castSpell). The limit is the spell's own (`getSustainLimit`: the "up to" part of `duration.value`, or the value, in rounds, minutes = 10 rounds, hours; 10 minutes only when none is listed, Sustain pg. 419). `sustainSpell` marks it Sustained this round (a GM note at the limit, nothing refused). onTurnStart posts what the creature is sustaining with Sustain and Stop buttons (`remindSustainedSpells`); onTurnEnd ends what wasn't cast or Sustained this round, or reached its limit, with a card and a GM button (`removeSpellEffects(spellName, casterTokenId)`) that removes the effects named exactly for the spell or "Aura: <spell>" from the scene's tokens; an effect that records its applier (`effectValues[id][].tokenId`) loses only this caster's instances (by `instanceIndex`, highest first). Spells don't record which effects they put on whom, so the GM applies them. onEncounterEnd clears the lists. Outside an encounter (no round) nothing ends.

### Critical specialization effects (buttons on a critical hit's card)

`rollhandlers/critical-specialization.js` (global script `CriticalSpecialization`). A critical hit with critical specialization keeps its description in the card's tag (getCriticalSpecializationDetails, PF2e.js) and gets its buttons from `getCriticalSpecializationButtons(weaponGroup, metadata)` (attack.js). The attack's metadata carries `critSpec` (`getCriticalSpecializationContext`: the attacker's class DC, the weapon's item bonus to attack, its damage dice). Spear (clumsy 1) and sword (off-guard) until the start of the attacker's next turn (`start_applier_turn`); brawling (slowed 1, until the end of its next turn), firearm and sling (stunned 1), flail (Reflex) and hammer (Fortitude, prone): a save button at the class DC and a separate On a Failure button, as the GM reads the result; crossbow, dart and knife: persistent bleed plus the item bonus (`applyPersistentDamageToToken`, split out of applyPersistentDamage); bow: immobilized; pick: its extra damage worked out; axe, club, polearm, shield, bomb: a line. Conditions go on with the attacker as applier (`applyCriticalSpecializationEffect`); "until the end of your next turn" (brawling, grievous sword) is marked `endOfNextTurn` and worked out on the click (`getEndOfNextTurnValue`), so a reaction's critical hit lasts the same. With a grievous rune in `metadata.runes`, a group's `grievous` entry replaces its fields: the stronger version (spear 2 rounds, sword end of next turn, dart 2d6, pick 4 per die, brawling and firearm saved against the DC + 4, crossbow the bow's immobilized, bow DC 20; knife and sling as notes).

### Exploration activities (H20)

`rollhandlers/exploration.js` (global script `Exploration`). The Skills tab's Exploration section (above Downtime, shown and editable when locked) has a dropdown bound to `data.explorationActivity` (also a party sheet column; "none" is no activity, `getExplorationActivity`). The field saves itself, so `record` is already up to date in its onchange; `setExplorationActivity` writes only the initiative skill, when it changes: Stealth for Avoid Notice, back to Perception from Stealth for any other choice. Every activity posts a line saying what it does (`getExplorationActivityNote`; Hustle's minutes from `data.con`). Scout: `getScoutInitiativeModifiers` passes a +1 circumstance bonus to initiative as `extraModifiers` (onRollInitiative.js) for any creature on the scout's side. `rollhandlers/onEncounterStart.js` (was empty) runs `startEncounterExploration(data.tokens)`: Defend raises an equipped, unbroken shield (record write + onAddEditFeature, lowered at turn start as usual), and the GM gets a card of everyone's activity with Avoid Notice's Stealth initiative against each foe's Perception DC (`getPerceptionDCForToken`) as Sneak's results in [gm] tags: undetected if met, hidden if missed by 1-9, observed by 10 or more (each with cover or concealment). Nothing is enforced.

### Recall Knowledge and Identify Magic (H22)

`rollhandlers/knowledge.js` (global script `Knowledge`), hooked into `performSkillAction` (the "Roll as" menus and action cards). Recall Knowledge with an NPC targeted rolls against `getKnowledgeDC` (`getDCForLevel` with `getItemRarity`, the level off under Proficiency without Level, as `getCraftingDC`), and the roll's metadata carries `gmNote` (`getRecallKnowledgeNote`): the skills the creature's traits call for (`CREATURE_IDENTIFICATION_SKILLS`, GM Core's Creature Identification table), a stretch at +2/+5 if the rolled skill isn't one, Lore at -2/-5, later attempts one step up GM Core's adjustment scale each from the rarity's step, ending at incredibly hard (`getLaterAttemptDCs` over `DC_ADJUSTMENT_STEPS`, as Foundry's `createDifficultyScale`; a unique creature has none; nothing tracks attempts), and a cheat sheet (the lowest save, the weaknesses). Identify Magic and Identify Alchemy first prompt for one of the character's unidentified items (`identified === false`, listed by `unidentifiedName`; alchemical items for Identify Alchemy, the others for Identify Magic, or "Something else" with no DC, `promptIdentifyItem`), then roll against `getIdentifyDC`: the item's level DC with its rarity, or incredibly hard in place of the rarity if cursed (Foundry's `getDcRarity`), then +5 with a skill outside its traditions (`TRADITION_SKILLS` from item-spells.js; magic without one takes any of the four, alchemical Crafting). The metadata also carries `gmMacro`, an Identify_Item button (`if (isGM) identifyInventoryItem(recordType, recordId, itemId)`, by id so the real name isn't in it) that sets `data.inventory.N.identified` in one write and notifies the GM (green when identified, yellow if it already is or the item is gone). It isn't `getChatButton`, which needs the character's token selected or dropped on: identifying usually happens off the scene. skill.js appends `gmNote` with every line in `[gm]` tags, then `gmMacro`. The dice show unless the Secret Checks setting is on (H23).

### Secret checks (H23)

The campaign setting `secretChecks` (off by default; GM Core lets a GM roll secret checks openly). With it on, `rollSkill` flags a check made as one of `SECRET_ACTIONS` (check-tools.js: the 15 actions whose records carry the secret trait, from Recall Knowledge to Sneak, plus an Influence encounter's Discover) with `metadata.secret` and `metadata.forcedAudience: "private"`. That undocumented flag opens the roll prompt (`api.promptRoll`/`promptRollForToken`) as a Private GM Roll and keeps it from being reset; the player can still change the Audience dropdown (we assist, we don't police). skill.js sends the usual card with `{ ...roll, audience: "private" }` when `metadata.secret` is set: Realm shows a private roll's dice and card only to the GM, and players see "Privately Rolled Dice". `api.sendMessage` honors `roll.audience`, so the card stays private even if the player switched the prompt, and Assurance (`api.roll`, which ignores `forcedAudience`; `getAssuranceMetadata` keeps `secret`) is private too. Don't send a secret card without its roll: `api.sendMessage` then uses the player's stored audience.

### Gear: broken items, talismans, runes (H34-H36)

`rollhandlers/item-gear.js` (global script `ItemGear`). Item HP and Hardness are the item sheet's otherProperties fields (`data.hp`, `data.hardness`); the modules leave them empty for most gear, so these apply once the GM fills them in.
- Broken (Player Core pg. 442): `isItemBroken` is the shield rule (`isShieldBroken`: HP at or below half the max; no max, never). In `getEffectsAndModifiersForToken` a broken item's bonuses are left out but its penalties stay ("a broken item still imposes penalties"): `getItemModifierSources` keeps only its `isPenaltyModifier` modifiers (a penalty type, or a negative number) for `modifierItems`, and `getUnbrokenItems` feeds `getFeaturesFromRunes`. Broken armor keeps its item bonus to AC (`getACForArmor`, potency too), loses its resilient rune, and takes `getBrokenArmorModifier`: a status `armorClassPenalty` of 1/2/3 by category (light/medium/heavy), 1 less for laminar. A broken weapon can't Strike, as a broken shield can't: `performAttackRoll` shows `getBrokenStrikeWarning` and rolls nothing.
- Repair (Player Core pg. 236): the item sheet's Repair button (`repairInventoryItem`, by the HP fields: the weapon and armor ones on the Rules tab, a shield's on the Main tab; field `repairBtn`, shown by `isRepairButtonHidden` for an inventory item with a max HP) rolls Crafting against `getCraftingDC(item)` with `metadata.repair`. skill.js adds `getRepairLines`: Restore N HP (`getRepairHp`: 5 + 5 per rank, 10 + 10 per rank on a critical success; `restoreItemHp`, read fresh, capped at the max) or, on a critical failure, Damage Item 2d6 (`damageRepairedItem`: `api.rollInstant`, less Hardness). Both strike out their card, write once, then run `onAddEditFeature` (a shield's HP, broken armor's AC). A destroyed item (0 HP) can't be Repaired.
- Talismans and spellhearts (GM Core pg. 263): the item sheet's Affix button (`promptAffixItem`, shown for `isAffixableItem`: an "affixed"/"applied" usage or the talisman or spellheart trait) sets the item's `data.affixedTo` (the host's `_id`; hosts by `getAffixHostTypes` of its usage). `getAffixDisplayValues` writes the host's `data.affixedLabel` and `fields.affixedBox.hidden`, the Affixed line with a Use button on its attack and inventory rows (`useAffixedItem`). A second talisman or spellheart on an item gets a notice (`getAffixWarning`) when affixed and on Use (`getAffixedUseWarning`); nothing is refused. A used talisman left in a stack isn't affixed any more (`getUsedTalismanValues`, in `useInventoryItem`'s write; a destroyed one drops off the host's line after). A spellheart counts as equipped only while `isAffixedItemActive`: affixed alone to an equipped item that isn't broken.
- Property rune limit (GM Core pg. 224): `getFeaturesFromRunes(items, record)` uses `getActivePropertyRunes`, as many as the potency value (`getPropertyRuneLimit`; under ABP the attack or defense potency); the rest are dormant. Picking runes or potency on the item sheet shows `getDormantRuneWarning`.
- Etching: the item sheet's Etch button (`promptEtchRune`, shown for an "etched" usage) reads the rune item's name (`parseRuneItem`: "Weapon Potency (+2)", "Striking (Greater)", "Resilient", "Reinforcing Rune (Minor)", or a property rune as "Advancing (Greater)" -> `greaterAdvancing`, checked against the dropdowns through `getWeaponRuneDetails`/`getArmorRuneDetails`; Energy-Resistant asks its energy), offers the items its usage allows (`getEtchHosts`: weapon, melee weapon, armor, light/heavy/medium-or-heavy armor, shield), and writes the inventory once (`getEtchValues`: the host's runes and `getItemFields`, the rune item taken out or one of its stack). It refuses a duplicate property rune or a lower fundamental grade. A reinforcing rune uses `getReinforcingRuneData`, shared with the shield's Reinforcing Rune dropdown.
- Transferring (GM Core pg. 225): the Crafting tab's Transfer a Rune button (`promptRuneTransfer`) picks the item and the rune (`getItemRunes`; reinforcing runes stay), looks up the rune item by name (`getRuneItemName`) for its level and Price, then picks an item that can take it (`getTransferTargets`: `getEtchHosts` by the rune item's usage, since anything else is an automatic critical failure; the same kind of item without the record). An item with the rune or an equal or better fundamental one gets Etch's notice (`getEtchedHostData`) and no project. Then it starts a Craft project (`buildRuneTransferProject` through `buildCraftProject`: 1 day, the level's DC, 10% of the Price, `output: "runeTransfer"`, `data.transfer`), paying the materials and rolling as a formula's project does. `getCraftProjectCompletion` moves the rune (`getRuneTransferValues`, through `getEtchedHostData`, so it moves nothing if the item has since got the rune or a better one) instead of adding an item. Swaps and runestones (free) are left to the GM.

### Data Structure

- Character data is nested under `record.data`
- UI state is under `record.fields`
- Lists (traits, features, etc.) typically have both array and object representations
- Always check for existing data before initializing defaults
